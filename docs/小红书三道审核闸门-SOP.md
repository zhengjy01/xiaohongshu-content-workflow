# 小红书工作流三道审核闸门 SOP

## 适用场景

小红书内容流水线从「每日选题雷达」到「发布归档」被**三道人工审核闸门**切成四段。本 SOP 是三道闸门的统一操作口径：闸门停在哪、谁放行、状态怎么取值、打回后怎么修订回流。

> 一句话：**本机（Obsidian 等）= 生产环境，手机端（Notion 等）= 移动审核台；agent 不得自动跨越任一闸门。**

## 三道闸门（定义）

| # | 闸门 | 停在哪一步 | 用户做什么 | 放行后才允许 |
| --- | --- | --- | --- | --- |
| 1 | **选题审核** | 每日选题雷达产出后 | 从当天雷达里挑一条（`待选题审核` → `已选题`），其余留池或 `已搁置` | 进入研究 + 成稿 |
| 2 | **生图前审核** | 出完「生图计划」后 | 审 **提示词全文 + 计划张数及用途 + 尺寸 1080×1440 + 模板**，可改、可放行、可打回 | 打开 ChatGPT 网页版真生图 |
| 3 | **发布前审核** | 成稿 + 全部配图齐备后 | 看完整稿与配图，决定 `已发布`（填 url）或 `已打回`（写原因） | 发布 → 归档；打回 → 修订后重回该闸门 |

**闸门 2 与闸门 3 都允许打回；打回必须带原因。** 任一闸门在用户明确放行前，agent 一律停下，**没有「先做着」的例外**。

## 状态取值（成稿 frontmatter `status`）

| 对象（frontmatter `type`） | `status` 取值与流转 |
| --- | --- |
| `选题` | `待选题审核` → `已选题`（用户挑中）／`已搁置` |
| `笔记` | `待生图审核` → `待发布审核` → `已发布` ／ `已打回`；打回后修订期间置 `打磨中`，修完放回**被卡住的那个闸门** |

- 选题候选可以没有独立 frontmatter；若雷达是 Markdown，可把状态落在候选条目下的 `- **审核状态**：…` 行。
- **权威方向**：内容字段（正文 / title / date / tags / 生图计划 / 配图）单向 **本机 → 审核台**；`status` / `url` / `review_note` 由**审核台权威回写**本机。
- 因此在手机上直接改正文/提示词会被下一轮同步覆盖——要改提示词，请在「审核意见」写清并置 `已打回`，由 agent 在本机改。

## 步骤

### 通用（每一道闸门都适用）

1. **agent 停在闸门前**：把该闸门的审核对象整理齐全并呈现给用户。
2. **等用户放行或打回**：不催促、不自作主张；闸门 2/3 收到打回时先读 `review_note`。
3. **按用户决定推进**：放行 → 下一步；打回 → 走「打回与修订闭环」。
4. **状态即事实**：状态只在用户操作后变更；agent 不自行把 `status` 推到下一闸门（`打磨中` 仅用于打回后的修订期）。

### 闸门 1：每日选题审核

1. 生成雷达（每个候选带来源原链接、证据等级），落固定目录。
2. 雷达交付后**写完即停**：置候选 `待选题审核`，**不得自行选题**继续研究/成稿。
3. 用户挑一条 → `已选题`；不做的置 `已搁置`。
4. agent 读到 `已选题` 后，才进入研究 → 成稿。

### 闸门 2：生图前审核

1. 成稿完成后定模板（数据内容默认 `infographic-engine`），产出「生图计划」四要素：**模板 / 提示词全文（结构化）/ 计划张数及每张用途 / 尺寸 1080×1440（PNG）**。
2. 把计划写进成稿 md 末尾的 `## 生图计划` 段（元信息 + ```text 提示词全文```）——这是同步到审核台「生图计划」块的**唯一来源**；不写进笔记，手机端只能看到占位提示。
3. 置 `待生图审核`，停下送审。
4. 用户放行 → 才允许打开 ChatGPT 网页版真生图；用户改提示词/张数 → 更新计划后重新送审；用户打回 → 按原因重写，重写后再送审。

### 闸门 3：发布前审核

1. 配图落附件库并在笔记内 `![[图名.png]]` 嵌入，成稿 + 配图齐备。
2. 置 `待发布审核`，把完整稿与配图交给用户。
3. 用户决定：
   - `已发布` → 填 `url`（回流时补 `publish_date`），归档；发布动作始终**人工在 App 完成**，agent 不发布。
   - `已打回` + 原因 → 走修订闭环。

## 打回与修订闭环

```
用户打回（status: 已打回 + review_note 写原因）
      ↓ 下一轮同步回写 frontmatter（status / review_note）
agent 先读 review_note → 置 打磨中 → 按原因修订
      ↓
status 放回被卡住的那个闸门（待生图审核 / 待发布审核）→ 重新送审
      ↓
用户再放行 → 继续；再打回 → 循环
```

- **打回必带原因**：写「图太花」「数据不突出」「张数不够」「标题不够痛」，不要只写「重做」。
- **agent 修订前必须先读 `review_note`**，不得凭印象猜。
- **打回不改匹配键**（如文件路径），不会产生重复记录。
- 闸门 2 的「说一句提示词重写」也算打回，同样要落成 `已打回` + 原因。

## 与本机 ↔ 审核台同步的协作方式（可选实现）

> 本仓库只带**流程与 skill 指令**，不带同步器。用一个「本机生产 → 手机审核台」的同步脚本即可落地，例如本机 Obsidian ↔ 手机 Notion：

- **入口**：手机端用一个「运营台页 + 内联内容库」承载三类对象——`type=选题`、`type=笔记`、笔记页内的「生图计划」块。
- **同步节奏**：定时器每 30 分钟一轮（首次全量、之后增量），也可手动跑。
- **三向 snapshot**（为什么必须）：单向同步会冲掉手机上刚改的 `status`，所以要有一个 state 文件记上次基线，每轮比较「本地内容 / 远端状态」：本地变 → 推正文（保留远端状态）；远端变 → 回写本机 frontmatter；两侧都变 → 内容推审核台、状态取审核台（人工权威）。
- **agent 依回流续跑**：一键看待办——`已选题` → 研究/成稿；`待生图审核` → 出/改生图计划；`待发布审核` → 等发布或打回；`已打回` → 读 `review_note` 修订后回到原闸门。
- **status 冲突规则**：远端 status 自上次基线变了（用户在手机上操作）→ 取审核台；远端没变、本地（agent）status 变了 → 推到审核台，让稿子进入/回到闸门。

## 注意 / 踩坑

- **「一条龙」≠「无人值守」**：流水线环节齐全，但被三道闸门切开；任何一环都不得自动跨越。
- **不自动发布**：小红书无开放 API，平台操作一律人工，agent 只负责内容与状态。
- **手机上改正文/提示词会被覆盖**：正文是本机单向权威；要改就走「审核意见 + 已打回」。
- **不要写入无关的库**：同步器要硬拦「绝不写入博客内容源」这类其它库，避免污染。
- **同步失败不改变闸门语义**：审核台通道不可用时，闸门仍成立——用户在对话里放行/打回同样有效。
